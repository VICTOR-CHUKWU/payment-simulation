### Claude

To clear one thing up first: there is no `process.close`. You probably mean `server.close()`, which belongs to the HTTP server, not the process. Here are the three pieces, all in [shutdown.ts](libs/shared/src/shutdown.ts).

## The problem they solve

When a service is stopped (Ctrl-C, `kill`, Docker or Kubernetes stopping a container), the operating system sends the process a **signal**:
- **SIGINT** is what Ctrl-C sends.
- **SIGTERM** is what `kill`, Docker and Kubernetes send.

By default Node dies immediately on either signal. A request being handled is cut off mid-way, and NATS messages waiting to go out are lost. We want the service to stop cleanly instead.

## `process.once`

`process` is Node's built-in object for the running program. `process.once("SIGTERM", handle)` means: "the first time a SIGTERM arrives, run my `handle` function instead of dying." `once` (rather than `on`) means it only catches the first one. If you press Ctrl-C a second time, Node's default comes back and the process dies at once. That gives you a way to force-quit if a clean stop hangs.

It is used in exactly two lines, [shutdown.ts:53-54](libs/shared/src/shutdown.ts#L53-L54), inside `onShutdown`.

## `server.close()`

`server` is the HTTP server that `app.listen(port)` returns. `server.close()` tells it to stop accepting new connections, let requests already in progress finish, and then call back to say "I'm closed."

It is called in `closeServer`, at [shutdown.ts:13-17](libs/shared/src/shutdown.ts#L13-L17), which just turns that callback into something we can `await`.

## `createShutdown` and `onShutdown`

These are two layers:

1. **`createShutdown`** ([shutdown.ts:19-42](libs/shared/src/shutdown.ts#L19-L42)) is the actual stopping routine, in order:
   1. Close the HTTP server.
   2. Run the cleanup tasks one by one. Today that is only "drain NATS" for payment and notification, which sends any pending messages and then disconnects.
   3. Return `0` if everything went fine, or `1` if something failed.

   If it is called twice, the second call doesn't repeat the work. It does not touch signals at all, which is why the tests can call it directly.

2. **`onShutdown`** ([shutdown.ts:44-55](libs/shared/src/shutdown.ts#L44-L55)) connects that routine to the signals. It uses `process.once` so that when SIGTERM or SIGINT arrives it:
   1. Starts a 10-second safety timer. If shutdown hangs, the timer force-exits with code 1.
   2. Runs the stopping routine.
   3. Records the result as the exit code. Node then exits on its own once nothing is left running.

## Where the services use it

Each service calls `onShutdown` once, as the last line of its `main.ts`:
- [auth/main.ts](services/auth/src/main.ts): `onShutdown({ server })` has no cleanup tasks, because auth has no NATS connection.
- [payment/main.ts](services/payment/src/main.ts) and [notification/main.ts](services/notification/src/main.ts): `onShutdown({ server, tasks: [() => nc.drain()] })` also drains NATS.

So the full chain is: Ctrl-C → SIGINT → `process.once` catches it → `onShutdown`'s handler → `createShutdown`'s routine → `server.close()`, then `nc.drain()` → the process exits with 0.

### Claude

Yes, mostly. A few details are worth knowing.

1. **The order is the other way around.** The server stops *first*: it refuses new connections, but requests already in progress are allowed to finish. *Then* the cleanup tasks run, which today means draining NATS so queued messages are sent before disconnecting. It goes: stop taking work → finish current work → clean up → exit.

2. **Ctrl-C isn't the main reason this exists.** In real deployments, Docker and Kubernetes stop a service with SIGTERM, for example on every deploy or restart. That's where clean shutdown really matters: without it, every deploy could cut off live payment requests. Ctrl-C (SIGINT) just gets the same treatment, so local runs behave the same way.

3. **A second Ctrl-C force-exits, yes.** There's also a second safety net: if the clean stop takes longer than 10 seconds, the process force-exits by itself, so a stuck shutdown never hangs forever.

One caveat from the review: under `pnpm dev`, the watcher (`tsx watch`) sits between your terminal and the service. If a single Ctrl-C reaches the service twice, once from the terminal and once relayed by `tsx`, the second copy would force-exit and skip the drain. I haven't tested that, so it's unconfirmed. It only affects local dev, not `pnpm start` or containers.
