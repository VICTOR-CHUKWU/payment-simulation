### Claude

JetStream is the part of NATS that stores messages.

**Plain NATS** is fire-and-forget. When a service publishes a message, NATS passes it to whoever is subscribed at that moment, then forgets it. If no one is listening, for example because the notification service is restarting, the message is lost.

**JetStream** is a storage layer built into the same NATS server, switched on by the `-js` flag in [compose.yaml](compose.yaml). It adds:

- **Streams:** messages on chosen subjects (such as `payment.*`) are saved to disk. In this project that's the `nats-data` volume, so they survive a NATS restart.
- **Durable consumers:** a named reader whose position in the stream NATS remembers. If the notification service goes down and comes back, it continues from where it stopped.
- **Acks and redelivery:** the consumer has to confirm each message. If it doesn't, because it crashed or the email send failed, JetStream sends the message again after a delay, up to a set limit.
- **Publish-side dedupe:** if the same message ID is published twice within a time window, JetStream keeps only one copy. That's the `Nats-Msg-Id` / `msgID` part of BE-01-02.

**Where this project uses it:**

1. **Payment → notification (BE-04-02):** when a payment succeeds or fails, the payment service publishes an event. JetStream stores it even if the notification service is down, so the user still gets notified.
2. **In-app and email as separate durable consumers (BE-05-01):** each reads the same events on its own. A broken mail server doesn't hold up in-app notifications.
3. **Email retries with backoff (BE-05-05):** a failed email isn't acknowledged, so JetStream sends it again later. This needs no retry code of our own.
4. **Dead-letter queue (BE-05-06):** after the last attempt, the handler moves the email to a separate `DLQ` stream so an admin can inspect it and send it again. JetStream has no built-in dead-letter stream, so the handler does this step itself.
5. **No duplicates on publish (BE-01-02):** `publishEvent` uses the event's ID as the message ID. If the payment service retries a publish, for example after a timeout, JetStream drops the copy.

**One catch:** JetStream guarantees each message is delivered at least once, not exactly once. A consumer can still receive the same message twice, for example if it crashes after sending an email but before acknowledging. That's why `AGENTS.md` requires idempotent consumers that dedupe by `eventId` plus channel (BE-05-02).

The line you highlighted only records that the local NATS from BE-01-03 already has JetStream switched on. BE-01-02 can rely on it, and the manual check in the doc was run against it.

### Claude

Short answers: keep the current folder layout, and keep config and events as functions. Classes will come in later milestones where they actually help.

### 1. Folder layout

An extra parent folder like `app/services` and `app/libs` wouldn't add anything, because the repo root already is the app. Monorepos normally keep deployable code and shared code side by side at the top level:

- Nx and Turborepo use `apps/` for deployables and `packages/` or `libs/` for shared code.
- This repo already follows that pattern as `services/` + `libs/`. For a backend-only repo, `services` is the clearer name for what's in it.

Renaming would touch `pnpm-workspace.yaml`, `jest.config.js`, `tsconfig.test.json`, the root `tsconfig.json` references, `AGENTS.md`, the README, the roadmap and every task doc, and it gains nothing. If you want the Nx-style names anyway, I'd rename `services/` to `apps/` and leave both folders at the top level. That's a cheap change now and gets harder as code lands.

### 2. Classes or functions for config and events

**Config:** it's read once at startup and never changes. A `Config` class would end up as a constructor that does what `loadConfig` already does, plus `this`. The inheritance you'd want from a class is already there through Zod: `baseConfigSchema.extend({ PORT: ... })` gives each service the shared fields plus its own, and the types follow automatically.

**Events:** these are data that travels over NATS as JSON. `JSON.parse` always returns plain objects, so a received event would lose its methods and fail `instanceof` checks. You'd have to rebuild class instances after every parse. That's why the usual practice is a plain object with a schema, which is what `eventEnvelopeSchema` and `createEvent` are.

**Where classes do fit:** things that hold state or have several implementations behind one interface. The roadmap already has those coming:
- **BE-01-06, errors:** a base `AppError` with subclasses like `NotFoundError` and `ValidationError`. Inheritance is the natural tool here.
- **BE-01-07 and BE-01-08, repositories:** a `Repository<T>` interface implemented by `InMemoryRepository` and `JsonFileRepository`. That's real abstraction: one interface, two interchangeable storage backends.
- **The NATS wrapper, maybe later:** if passing the JetStream client into every call gets awkward when BE-01-04 wires it into the services, an `EventBus` class that holds the connection would be reasonable. Right now it would be a class for its own sake.

So the rule I'd follow: use plain functions and Zod schemas for data and one-off setup, and classes for stateful pieces with several implementations. Nothing needs to change in the current branch. Tell me if you want the `apps/` rename and I'll do it.
