### Claude

This doc doesn't make the services talk to each other yet. It does two setup jobs that have to happen first:

1. **It fixes the message format.** The payment and notification services agree on five event names, one per status change, and on what each message contains. For example, a `payment.failed` message carries the payment ID, the user's ID and email, the amount, the currency and the failure reason.
2. **It makes sure the `PAYMENTS` stream exists in NATS.** Each service checks for it when it starts and creates it if it's missing.

Both services already connect to NATS today; that was done in BE-01-04. But neither one sends or receives anything over that connection yet. Sending starts in BE-04-02, when the payment service publishes a message whenever a payment changes status. Receiving starts in BE-05, when the notification service reads those messages to send emails and in-app notifications.

**What a stream is**

Plain NATS only delivers a message to services that are listening at that moment. If the notification service is down when a payment succeeds, that message is lost.

JetStream is the part of NATS that stores messages. A stream is a stored list of messages, saved on disk, for a set of subjects. A subject is the name a message is published under, like `payment.succeeded`.

This doc defines one stream:

| Setting | Value | What it means |
|---|---|---|
| Name | `PAYMENTS` | The stream's name |
| Subjects | `payment.>` | It stores every message whose subject starts with `payment.` |
| Storage | File | Messages survive a NATS restart |
| Kept for | 7 days | Older messages are deleted |
| Duplicate window | 2 minutes | If the same event is sent twice within 2 minutes, NATS stores only one copy |

Here's how it will work once BE-04-02 and BE-05 land. The payment service publishes `payment.succeeded`, and NATS saves it in `PAYMENTS`. The notification service reads it when it's ready, even if it was down when the message was sent. It marks each message as handled once it has processed it. If it crashes before marking a message, NATS sends that message again. That's why consumers have to be safe to run twice on the same event.

Both services create the stream because either one might start first. The notification service can't set up its message reader on a stream that doesn't exist.

### Claude

That's expected. `pnpm infra:reset` doesn't touch those files.

`infra:reset` runs `docker compose down -v`. That stops the Docker containers and deletes their volumes, which only hold the NATS JetStream data: streams and messages. It doesn't touch anything outside Docker.

`users.json` and `payments.json` are the services' own storage, written by the JSON-file storage on your disk in `services/<service>/data/`. Those files are meant to survive restarts, and resetting the message broker is a separate thing. The README describes this at [README.md:126](README.md#L126).

To start fresh:

1. Stop `pnpm dev` first. The services hold a lock on the files and write to them as they run.
2. Delete the data folders:
   ```sh
   rm -rf services/auth/data services/payment/data
   ```
3. Start again. Auth re-seeds the demo admin and user, and payments start empty.

If you'd rather nothing be saved while you're testing, set `STORAGE_DRIVER=memory` in `.env`. Then all data is gone whenever a service stops.

For a full clean slate, delete the data folders and run `pnpm infra:reset` too. That removes the users, payments and NATS streams.

It was claimed at 10:25:57.99 and failed at 10:26:08, which is your `GATEWAY_TIMEOUT_MS=10000`. With `GATEWAY_TIMEOUT_RATE=0.05` in your `.env`, about 1 payment in 20 does this on purpose.

**Is "failed" misleading?** In this simulation, no. In a real payment system, yes.

- **Here:** when the simulated gateway "hangs", it never charges anything. So when the processor gives up after 10 s, the payment really didn't go through, and `failed` is accurate. This was a deliberate choice in BE-03-05, so the timeout path can be exercised and every payment ends up final.
- **In real life:** a timeout means the outcome is unknown. The bank may have charged the card and the reply got lost. Marking that `failed` could lead a user to pay twice. Real systems keep the payment open and check with the gateway later, using the payment ID as the idempotency key, before deciding.

The BE-03-05 doc weighed this. It rejected leaving timed-out payments `processing` forever, because one that always hangs would never finish. It also rejected retrying before failing, which it judged as more complexity than this project needs.

**What I'd do:** keep the behavior for this project, and make the README say plainly that a simulated timeout means the gateway never charged, unlike a real one. If you want it closer to reality, the realistic change is to retry a timed-out payment a few times, then fail it. That's safe because resubmitting with the same payment ID can't charge twice. It touches the processor and config, not the event catalogue. An "unknown" status would be heavier, because it changes the state machine and the five events we just defined.

To stop seeing timeouts while you test locally, set `GATEWAY_TIMEOUT_RATE=0` in `.env`.
