## Should logs include the user's email?

The usual practice (OWASP Logging Cheat Sheet, GDPR data minimisation, how Stripe and others log) is to **identify the user by their ID, not by personal data like email**:

- Logs get copied to more places than the database (log shippers, vendor dashboards, support exports) and are kept longer. An email in a log line is personal data you then have to protect and delete everywhere it went.
- `userId` (the JWT `sub`) is stable and unique. Anyone debugging can look up the email from the auth store when they actually need it.
- Emails can change, and a "delete my data" request can't reach emails already written to logs.

So for "show user details if the user exists," the standard is: **every request log line from an authenticated user carries `userId` and `role`**, and unauthenticated lines leave the fields out. If someone needs to read an address while debugging, the compromise is a **masked email** (`c***@gmail.com`). It's recognisable but can't be used to contact anyone or join data across systems.

There's a timing catch. The user isn't known until JWT middleware exists in BE-02-03. So BE-01-05 builds the mechanism (a request-scoped logger plus a helper that attaches the user to it), and BE-02-03 calls that helper after verifying the token.

## What the logger does

A log is the service's diary. Each time something happens (a request comes in, a payment fails, the service starts), it writes one line about it. With pino, each line is a small piece of JSON rather than a sentence, so tools can search and filter it:

```json
{"level":"info","time":"2026-10-18T10:00:00Z","service":"payment","msg":"listening","port":3002}
```

The plan adds three pieces in the shared library:

1. **`createLogger`** builds the diary for one service. It stamps every line with the service name and the time, and decides how much detail to write based on `LOG_LEVEL`. In development the lines print as coloured, readable text; elsewhere they stay JSON.
2. **`httpLogger`** is middleware that watches every HTTP request. When the request finishes, it writes one line saying what came in, what status went back and how long it took.
3. **Redaction** is a filter. Before a line is written, it replaces passwords, tokens, the `authorization` header and emails with `"[Redacted]"`, so secrets never end up in the logs.

## What `correlationId` is

It's a **tracking number for one request**, like a parcel tracking number.

Many requests hit the services at the same time, so their log lines get mixed together. Suppose a user reports that their payment failed. Without a shared ID, you can't tell which of thousands of lines belong to that user's request.

So when a request arrives, the service gives it an ID (for example `7f3a…`) and stamps that ID on **every log line about that request**, as `correlationId`.

It also travels **between services**. When the payment service publishes a "payment failed" event over NATS, it puts the same ID in the event header (`x-correlation-id`). The notification service reads it and stamps its own log lines with it too.

The result: one search for `correlationId = 7f3a…` shows the whole story across services, in order:

```
payment       correlationId=7f3a  POST /payments → 201 pending
payment       correlationId=7f3a  gateway declined payment
notification  correlationId=7f3a  in-app notification stored
notification  correlationId=7f3a  email sent
```

## Where the ID comes from

- If the caller sends an `x-request-id` header with a safe value (short, plain characters), the service reuses it. That lets a frontend or gateway trace its own call end to end.
- Otherwise the service generates a random ID.
- Either way, it sends the ID back in the response's `x-request-id` header. A user or frontend developer can quote it in a bug report, and you search the logs for exactly that ID.

## Where the user fits in

Once login checks exist (BE-02-03), lines for a logged-in request also carry `userId` and `role`. That's how you see *who* made the request, without putting their email in the logs.

So a full request line ends up roughly like this:

```json
{"level":"info","service":"payment","correlationId":"7f3a…","userId":"u_42","role":"user","req":{"method":"POST","url":"/payments"},"res":{"statusCode":201},"responseTime":12,"msg":"request completed"}
```

In short, `correlationId` answers "which request is this line about?", and `userId` answers "whose request was it?"

### Claude

I'd keep them where they are. Grouping code by kind (a `constants/` folder, an `interfaces/` folder) is generally worse than keeping each constant and type next to the code that uses it, and in this lib it wouldn't remove any duplication.

**Why I'd leave them:**

- **Nothing is repeated.** Each constant and interface is used in exactly one file. `REQUEST_ID_PATTERN` and `REDACT_PATHS` only mean something inside `logger.ts`, and `ShutdownOptions` only inside `shutdown.ts`. DRY is about removing copies, and there are none to remove here.
- **Private values would become public.** Today `REDACT_PATHS`, `REQUEST_ID_PATTERN` and `boundUsers` aren't exported, so no service can depend on them or change them. Moving them into separate files means exporting them, so they become part of the lib's surface and are harder to change later.
- **Changes would touch more files.** Changing redaction would mean editing `constants/`, `interfaces/` and `logger.ts` together instead of one file. Most TypeScript style guides favour organising by feature for this reason.
- **There's already one clean entry point.** [index.ts](libs/shared/src/index.ts) is the single place services import from, so they never see the internal layout.

**When a shared file does make sense:** when a value really is used by several modules. The two header names (`x-correlation-id` in `nats.ts` and `x-request-id` in `logger.ts`) are the only candidates. Even those are each used by one module today, so I'd wait until a second module needs one.

**If the lib grows:** split by feature, not by kind. For example, `logger/` with `logger.ts`, `types.ts` and `logger.test.ts`, so each feature still sits in one place.

If you'd still like the `constants/` and `interfaces/` layout, I can do it. It's a mechanical move with no behaviour change, and I'd confirm it with check, typecheck, test and build. Which way do you want to go?
