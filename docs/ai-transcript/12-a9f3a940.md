## Draft scope for BE-02-03

**Goal:** add shared Express middleware to `libs/shared` that verifies the JWT access tokens `auth` issues, plus a role guard. Payment and notification will use it from BE-03-02 onwards.

**Already settled by earlier task docs:**
- **Shared contract (already exists):** `libs/shared/src/auth.ts` already holds `accessTokenClaimsSchema`, `roleSchema`, `jwtConfigSchema` and `resolveJwtSecret`. Auth signs tokens with HS256 through `jose` 6.2.12 in [auth.token.ts](services/auth/src/auth/auth.token.ts).
- **How to verify:** the BE-02-02 follow-up at [tasks/BE-02-02-auth-register-login.md:248](tasks/BE-02-02-auth-register-login.md#L248) says:
  - add `jose` to `libs/shared`
  - verify with `algorithms: ["HS256"]` and parse the payload with `accessTokenClaimsSchema`
  - return `401` with `WWW-Authenticate: Bearer`
  - call `bindLogUser`
  - payment and notification configs extend `jwtConfigSchema` and call `resolveJwtSecret`
- **Logging:** BE-01-05 says to call `bindLogUser(req, res, { userId: sub, role })` and never pass `email`. The logger already redacts the auth header.
- **Errors:** BE-01-06 says to use `unauthorized` / `forbidden` and never reveal internals in the error text.
- **OpenAPI:** BE-01-09 says protected routes set `security: bearerSecurity` and include `problemResponses(401, 403)`. Both already exist in [openapi.ts](libs/shared/src/openapi.ts).

**What I'd build:**
- **`authenticate(secret)`:**
  - Reads `Authorization: Bearer <token>`, case-insensitive on the scheme.
  - Verifies the token with `jwtVerify`, accepting only HS256, then parses the claims with the shared schema.
  - On success, binds the user to the request's log lines.
  - A missing header or one that isn't a Bearer token returns `401` with `WWW-Authenticate: Bearer`.
  - A token that's bad, expired, signed with the wrong algorithm, or has claims that fail the schema returns `401` with `code: "invalid-token"` and `WWW-Authenticate: Bearer error="invalid_token"` (the RFC 6750 form). The response gives the same detail for every failure.
- **`requireRole(...roles)`:** returns `403` (plain `forbidden`) when the token's role isn't in the list.
- **No call to the auth service at runtime.** Role and email come from the token. A role change only takes effect once the old token expires, which is at most 24h. I'll record that trade-off in the doc.
- **Tests:** unit tests plus supertest against a small Express app built inside the test. They cover:
  - a valid token
  - a missing header, a wrong scheme and a malformed token
  - an expired token, a wrong secret, `alg: none` / HS512, and claims that fail the schema
  - a role mismatch
  - `userId` and `role` appearing on the log lines, with no email or token in them
- **README:** add a short note on the 401/403 codes to the Errors section.

**Out of scope:** checking that the user still exists, token revocation, refresh tokens, and the `iss`/`aud` claims (auth doesn't set them).
