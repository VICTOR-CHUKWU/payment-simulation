### You

> so explain this doc in plain term, are we using cron job or a queue like bullmq how do we handle this backgound process or does node have an inbuilt one?

### Claude

Neither. There's no cron job and no BullMQ. The background work uses Node's built-in timers (`setTimeout`), running inside the payment service process. No library and no extra infrastructure.

## What the doc describes

Picture a clerk who checks an inbox every second:

1. **Check the inbox.** About once a second, the processor looks through the stored payments for any that are `pending`.
2. **Claim it.** It changes the payment to `processing`, so nothing else picks it up.
3. **Send it to the "bank".** The simulated gateway is a fake bank. It waits a random 1–5 seconds, then says "approved" or "declined". Sometimes it never answers, to simulate a hung bank.
4. **Record the answer.** The payment becomes `succeeded` or `failed`. If the bank hasn't answered after 10 seconds, the processor gives up and marks the payment `failed` with the reason "Gateway timed out".
5. **Repeat.**

## Where's the queue?

The payments data is the queue. A payment whose status is `pending` is a job waiting to be done, and `processing` means it's being worked on. Because those statuses are saved in the JSON file, a restart doesn't lose any work. On startup, the processor finds payments still marked `processing` and sends them to the gateway again.

## Does Node have something built in?

Node has no built-in job queue, but it has the two things this needs:

- **Timers:** `setTimeout` runs the "check the inbox" step on a schedule.
- **Async I/O:** while a payment waits on the fake bank's delay, Node keeps serving HTTP requests. Waiting doesn't block anything.

That's enough here because there's one payment service process and the work is light.

## Why not BullMQ or cron?

- **BullMQ** needs Redis. The roadmap's Decisions table rules Redis out, and the roadmap says the processor updates status inside the payment service itself, not over HTTP or a message bus. BullMQ would earn its place with many service instances sharing work, or with heavy jobs that need retries, priorities and a dashboard. Neither applies here.
- **Cron** suits jobs that run at set times, like every hour or every night, and the usual Node cron libraries don't go finer than one second. Here a payment should be picked up within about a second of being created, and a plain timer does that with less setup.
- **NATS** (which the project already uses) could act as a queue too. It's reserved for messages between services, such as telling the notification service that a payment succeeded.

## Trade-offs

- **Pickup can lag by up to one check interval** (1 second by default). That's fine when the fake bank takes 1–5 seconds anyway.
- **It assumes one payment service instance.** Two copies would both see the same `pending` payment. The save step refuses an update to a record that changed since it was read, so only one copy's claim would succeed. Even so, scaling out would call for a real queue or a claim system, which the doc lists as out of scope.

### You

> so u say it runs every second 
> so the first round picks 5 will it mark it processings so the next second timer wont pick the same 5 again?

### Claude

Yes. Two things stop the next round from picking up the same payments.

**1. The status change.** When the first round claims a payment, it saves it as `processing` before calling the fake bank. A second later, the next round looks for `pending` payments, and those 5 aren't `pending` any more.

**2. The in-flight list.** The processor keeps an in-memory list of the payment IDs it's working on. This matters because a round looks for `processing` payments too, so it can resume ones left over from a restart. Without the list, the next round would see the 5 that are `processing` and send them to the bank again. With it, the rule is "only resume `processing` payments that aren't on my list." After a restart the list starts empty, so leftover `processing` payments get picked up, which is what we want.

**The limit of 5 counts work that's still running.** Each round takes "5 minus however many are already in progress", not 5 new payments:

```
second 0: 12 pending, 0 in progress → claims the 5 oldest (5 in progress)
second 1:  7 pending, 5 in progress → 0 free slots, claims nothing
second 2: the bank answers 2 payments → 3 in progress
          next round: 2 free slots → claims the next 2 oldest
```

**Rounds never overlap.** The next round is scheduled only after the current one finishes, so if a round runs long, two rounds can't run at once and grab the same payment.

**An admin acting at the same moment is covered too.** Say a payment is `pending` and an admin cancels it at the same moment a round tries to claim it. The save step only accepts an update to the version that was read, so only one of them succeeds. If the admin's change lands first, the processor sees the payment is `cancelled` and skips it.

> so i want to understand something, when u mention abort or the sweep failed would the user see that reason? or its just a log for us to see cos i dont think user should see something like sweep failed

### Claude

Those are server logs only, for us. A user never sees "sweep failed", "aborted" or any other log message.

**What a user can see** is the payment returned by `GET /payments/:id`, which has only two fields the processor sets:

- **`status`:** `pending`, `processing`, `succeeded`, `failed` or `cancelled`.
- **`failureReason`:** only present when the status is `failed`. The processor only ever sets one of four values:
  - `Card declined`
  - `Insufficient funds`
  - `Issuer unavailable`
  - `Gateway timed out`

An admin's `PATCH` can also set `failureReason` to whatever text the admin types.

**What each internal problem looks like to the user:**

| What happened inside | What gets logged (for us) | What the user sees |
|---|---|---|
| Reading the payments failed during a check | `payment sweep failed` | The payment stays `pending` a little longer, until the next check works |
| Shutdown cancelled a waiting gateway call | Nothing beyond the shutdown lines | The payment stays `processing`, then settles normally after restart |
| The result couldn't be saved | `payment processing failed` | The payment stays `processing`, then it's sent to the gateway again and settles |
| An admin settled it first | `payment already settled` | The admin's result |
| The gateway declined | `payment processed` | `failed` with a reason such as `Card declined` |
| The gateway didn't answer in time | `payment processed` | `failed` with `Gateway timed out` |

When something goes wrong internally, the user just sees a payment that takes a bit longer to settle. No error text reaches them. The full error details, such as stack traces, go only to the logs, which is where [processor.service.ts](services/payment/src/processor/processor.service.ts) sends them.

**One thing you might want to change:** `Gateway timed out` is user-facing, and so are the decline reasons. Later, the notification service (Phase 5) will probably include `failureReason` in the in-app message and the email. "Gateway timed out" is a bit technical for a customer. If you'd prefer something like "The payment provider did not respond", it's a one-line change to `GATEWAY_TIMEOUT_REASON` plus the README and task doc.
