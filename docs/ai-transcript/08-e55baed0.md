## BE-01-08 inventory: JSON-file repository adapter

**Classification:** feature-grade. It adds a new persistent-state contract, and AGENTS.md lists BE-01-08 as needing an approved task doc.

**Objective:** add `createFileRepository<T>()` to `libs/shared`. It implements the existing `Repository<T>` contract, passes the same contract tests as the in-memory adapter, and survives restarts and crashes without corrupting data or losing a write it has already confirmed.

### Current state
- The `Repository<T>` interface has `get`, `find`, `insert` and `update` (compare-and-set on `version`), plus three error types ([repository.ts](libs/shared/src/repository.ts)).
- The in-memory adapter does each check-then-write in one synchronous step ([memory-repository.ts](libs/shared/src/memory-repository.ts)). The file adapter can't do that, because it has to wait for disk writes between the check and the write.
- The contract tests already run once per adapter from an `adapters` list, and each adapter's setup may be async ([repository.test.ts:24-28](libs/shared/src/repository.test.ts#L24-L28)).
- BE-01-07 left these for BE-01-08: the storage env var, choosing the adapter, Zod validation of loaded records, and a storage readiness check.
- `services/*/data/` is already gitignored. `pnpm dev` runs each service from its own folder, so a `data` directory resolves to `services/<svc>/data`.
- Known problem from the handoff notes: pnpm sends Ctrl-C to the service twice, so the second signal force-exits and skips cleanup. Any lock file can therefore be left behind, and recovering from a stale lock is required, not optional.

### Proposed scope
**`file-repository.ts`: `createFileRepository<T>({ file, schema, logger? })`**
- **Model:** the whole file is loaded into memory when the repository opens. Reads come from memory. Every insert or update rewrites the full file. This matches the Persistence row in the roadmap's Decisions table.
- **File format:** `{ "formatVersion": 1, "records": [...] }`. Records are stored as an array so insertion order survives a restart. It is indented with 2 spaces so it's easy to read during the demo.
- **Serialized writes:** all inserts and updates go through one queue per file. Each operation checks the version, writes to disk, and only then updates memory and returns. A write that fails rejects the operation and leaves both memory and the file unchanged. Reads never see data that hasn't been saved.
- **Atomic write** (same steps as `write-file-atomic`):
  1. Write to a temp file in the same directory, named with the pid and a random suffix.
  2. `fsync` the temp file.
  3. `rename` it over the real file.
  4. `fsync` the directory.
  5. If any step fails, delete the temp file.
- **Opening the file:**
  - If the file is missing, start empty and create the directory with mode `0o700`.
  - Delete leftover temp files from a crash.
  - Check the envelope and every record against the Zod schema. Bad JSON or a record that fails the schema stops the open with an error naming the path, and the file is never overwritten.
  - Data files use mode `0o600`, because the users file will hold password hashes.
- **One writer per file:**
  - Within a process, opening a path that is already open throws an error.
  - Across processes, the repository holds a `<file>.lock` file created with `wx` (fails if it exists) that contains the owner's pid. If the pid in an existing lock is no longer running, the lock is stale and gets taken over. If that process is still alive, the open fails immediately.
- **`close()`** waits for queued writes, releases the lock, and makes any later call reject. It is registered as a shutdown task.
- **Storage readiness check** `storageCheck(repo)`: fails after a write fails and passes again after the next successful write.

**Choosing the adapter**
- Add an exported `storageConfigSchema` with two settings:
  - `STORAGE_DRIVER`: `memory` or `file`, default `file`.
  - `DATA_DIR`: default `data`.
- Add a helper `openRepository({ config, name, schema })` that returns the repository, a `close` function and a readiness check, whichever driver is chosen.
- Services start using it in BE-02-01, BE-03-01 and BE-05-03. Until then, the README and `.env.example` don't mention these variables, because they would have no effect yet.

**Tests**
- Add `["file", …]` to the contract adapters, using temp directories that are deleted afterwards.
- File-specific tests:
  - data and insertion order survive closing and reopening
  - 20 inserts started at once are all saved
  - injected failures in write, fsync and rename leave memory and the file unchanged, with no temp file left over
  - corrupt JSON or schema-invalid records make the open fail
  - a missing file opens empty
  - leftover temp files are deleted on open
  - opening the same path twice in one process fails
  - a lock held by a live pid blocks the open; a lock left by a dead pid is taken over
  - `close` waits for pending writes, and calls after `close` reject
  - the readiness check goes from failing back to passing
  - `openRepository` picks the adapter matching `STORAGE_DRIVER`
- Disk calls go through an injectable `fs`-like dependency, so the tests can use hand-written stubs. Native ESM Jest has no `jest.fn` here.

**Docs:** set the BE-01-08 roadmap row to the task doc link and its status. The README changes come with BE-02-01.

### Excluded
- Combining several pending writes into one disk write (steno does this). It conflicts with "an operation only returns after its data is saved".
- Backups, file rotation, append-only journals, and migrations between file format versions.
- Delete, pagination and indexes (as in BE-01-07).
- Connecting the services to storage.
- macOS's stronger flush (`F_FULLFSYNC`).

### Decisions to confirm (my recommendation first)
1. **Locking across processes:** the pid lock file with stale-lock takeover described above. The alternatives are locking within one process only, which is what lowdb does but leaves nothing stopping two processes, or adding the `proper-lockfile` dependency, which detects stale locks by file age.
2. **Durability:** `fsync` the file and the directory on every write. The alternative is rename only, which is faster but can lose the last write if the power fails.
3. **Validating loaded data:** a Zod schema is required for every file repository. The alternative is trusting the file as-is.
4. **Default driver:** `file`, so the demo keeps its data across restarts. The alternative is `memory`, which writes no files but loses everything on restart.
5. **New dependencies:** none; Node's `fs/promises` covers everything.

> is it like if i signup a user it will write it in a json file and read from the json file too?

### Claude

Mostly yes, with one difference: **it writes to the file on every change, but only reads the file once, when the service starts.**

Here's what would happen with signup once the auth service uses it (that's BE-02-01; nothing uses the adapter yet):

1. **Service starts.** The adapter reads `services/auth/data/users.json` once, checks every record against the user schema, and keeps all users in memory. If the file doesn't exist yet, it starts with no users.
2. **You sign up.** `insert` adds the user, then rewrites the whole file with the new user included. Only after the file is safely on disk does it update memory and return. The 201 response goes out after that.
3. **You log in, or anything else reads users.** `get` and `find` answer from memory without touching the file. That's fast, and it's safe because memory always matches what's on disk.
4. **You restart the service.** Step 1 runs again, so your user is still there. The in-memory adapter (`STORAGE_DRIVER=memory`) would have lost it.

The file would look like this:

```json
{
  "formatVersion": 1,
  "records": [
    { "id": "…", "email": "ada@example.com", "passwordHash": "…", "role": "user", "version": 1 }
  ]
}
```

The rest of the task doc is about making that file safe:

- **Atomic writes.** It writes a temp file, then renames it over the real one. A crash mid-write leaves you with the old file or the new one, never half a file.
- **One write at a time.** Two signups at the same moment are queued, so neither overwrites the other. The version check that stops two updates to the same record from both succeeding still works.
- **Lock file.** Only one process can own `users.json`. If a crash leaves an old lock behind, the next start takes it over.
- **Validation on load.** If someone hand-edits the file into something invalid, the service refuses to start instead of silently overwriting it.

It's basically a tiny database whose storage is one JSON file per service. It's fine for this project, with one instance per service and small data. It wouldn't scale to large datasets or several instances sharing a file.

> so what is the in memeory now...more like a Map or what

### Claude

Yes, it's literally a JavaScript `Map`. Here's the setup line from [memory-repository.ts:16](libs/shared/src/memory-repository.ts#L16):

```ts
const records = new Map<string, T>();
```

The key is the record's `id` and the value is the record. The four methods work on that Map:

- `get(id)` → `records.get(id)`
- `find(predicate)` → loops over `records.values()` and filters
- `insert` → checks `records.has(id)`, then `records.set(id, { ...record, version: 1 })`
- `update` → checks the version matches, then `records.set(id, merged record with version + 1)`

It does two extra things beyond a plain Map:

- **It copies data on the way in and out** (`structuredClone`). If your code changes the object it got back, the stored record doesn't change. Only `update` can change it.
- **Each method does its check and its write together, with no waiting in between.** Node runs one piece of code at a time, so two updates can't both pass the version check.

The Map lives inside the Node process and nothing else, so restarting the service empties it. That's the gap the JSON-file adapter fills. The file adapter also keeps its data in memory, as a list rather than a Map, and saves a copy to disk on every write so it can reload it at startup.

### Claude

Nothing happens yet if you create a user or a payment, because those endpoints don't exist. Register and login come in BE-02-02, and `POST /payments` in BE-03-02. No service calls the new storage code until then. Below is how it will work once they do.

**The two adapters are alternatives.** A service uses one of them, never both, and the `STORAGE_DRIVER` env var picks which:

- **Memory adapter** (`createMemoryRepository` in `memory-repository.ts`). It keeps records in a JavaScript `Map` and nothing else. When the service restarts, the data is gone.
- **File adapter** (`createFileRepository` in `file-repository.ts`). It also keeps records in a `Map` in memory, but saves a copy to a JSON file after every change. When the service starts, it reads that file back into the `Map`.

The overlap you noticed is real but internal: the file adapter has its own in-memory copy. It doesn't use the memory adapter.

Both have the same four methods (`get`, `find`, `insert`, `update`), defined by the `Repository` interface in `repository.ts`. Code that handles a signup or a payment calls those methods without knowing which adapter is behind them.

**`storage.ts` is the switch.** At startup a service calls `openRepository` with a name, such as `users`, and a Zod schema. It reads the config and returns one of these:

- With `STORAGE_DRIVER=memory`: a memory repository.
- With `STORAGE_DRIVER=file`, the default: a file repository at `<DATA_DIR>/users.json`, for example `services/auth/data/users.json`.

It also returns a `close` function for shutdown and a readiness `check` for `/health/ready`. `storageConfigSchema` in the same file defines the two env vars and their defaults.

**What signup will do once BE-02-02 is built**, using the file driver:

1. The auth service validates the request and hashes the password.
2. It calls `repository.insert({ id, email, passwordHash, role })`.
3. The file adapter puts the insert in its write queue, so two signups can't overwrite each other.
4. It checks the ID is new, writes all users to a temp file, syncs it to disk, renames it over `users.json`, and syncs the folder.
5. Only then does it add the user to its in-memory `Map` and return. The service responds 201.
6. Login later calls `find` to look up the email. That reads from memory and doesn't touch the file.

**Creating a payment will work the same way**, with the payment service's own file, such as `services/payment/data/payments.json`. When the processor later changes the status, it calls `update(id, version, { status })`. If an admin changed that payment in the meantime, the version won't match and the update is rejected with `VersionConflictError`.
