### Claude

Yes, it works the same way as the processor. On `pnpm dev`, [main.ts](services/payment/src/main.ts) calls `relay.start()`. That runs a sweep straight away, before any timer delay, and then repeats it every `OUTBOX_RELAY_INTERVAL_MS`.

Each sweep ([outbox.relay.ts:97-112](services/payment/src/outbox/outbox.relay.ts#L97-L112)) does this:

1. Reads every payment whose `outbox` has at least one entry, using `payments.find(...)` on the repository (the JSON file, in dev).
2. Sorts them by `createdAt`, so older payments go out first.
3. Publishes each payment's entries in array order. If a publish fails, it stops working on that payment and leaves the failed entry and everything after it for the next sweep.
4. Removes only the entries that were published, using a compare-and-set update. It re-reads the payment first, so any event a transition added during the sweep is kept.

So any events left over from the last run, for example after a crash or after NATS was down, go out on that first sweep.

**How it differs from the processor:**
- **No claiming and no concurrency.** The processor marks payments as `processing` and runs several at once. The relay works through payments one at a time and changes nothing except the outbox array.
- **It is also woken on demand.** The routes and the processor call `relay.kick()` when they add an outbox entry, so events don't wait for the next interval. The timer is a fallback.

**Restart edge case:** the relay can crash after publishing an event but before removing it from the outbox. On the next start, that event is published again. JetStream drops the repeat if it arrives within the stream's 2-minute duplicate window, because the message ID is the `eventId` ([nats.ts:49](libs/shared/src/nats.ts#L49), [streams.ts:34](libs/shared/src/streams.ts#L34)). Outside that window, the consumers' idempotency (the `eventId` + channel dedupe) handles it.
