- `toPaymentResponse` already strips `version` and `idempotencyKey`, and `paymentResponseSchema` is registered under the OpenAPI ID `Payment` ([payment.service.ts](services/payment/src/payment/payment.service.ts), [payment.schema.ts](services/payment/src/payment/payment.schema.ts)).
- The repository has `get(id)` ([repository.ts](libs/shared/src/repository.ts)). Payment `id` and `userId` are UUIDs ([payment.ts:47](services/payment/src/payment/payment.ts#L47)).
- The shared code already provides `getAuth(req)` (returns `sub`, `email`, `role`), `requireRole`, `notFound` and `problemResponses` ([auth-middleware.ts](libs/shared/src/auth-middleware.ts), [errors.ts](libs/shared/src/errors.ts)).
- The BE-03-02 and BE-03-07 task docs both say BE-03-03 should reuse `paymentResponseSchema` and `toPaymentResponse`.

**Proposed scope**
- `PaymentService.get(id, caller)` returns a `PaymentResponse`, or throws `notFound` with the code `payment-not-found`.
- A `controller.get` handler: parse `:id` with Zod `z.uuid()`, return `200` with the payment.
- Route `GET /payments/:id` behind `authenticate`.
- OpenAPI registration: `200` with `Payment`, plus problem responses for `400`, `401` and `404`.
- A README payment-endpoints row and a curl example. Flip the roadmap status.
- Tests: service unit tests and supertest route tests for found, unknown ID, malformed ID, no token, and the ownership cases.

**Defaults I'll use unless you object**
- A malformed ID returns `400 validation-error`, consistent with the rule that HTTP input is validated with Zod at the boundary.
- The response is the stored payment as it is now, with no caching or ETag.

**Out of scope:** list endpoints (BE-07-02), `PATCH` status changes (BE-03-04), and admin-only `PATCH` (BE-03-06 or BE-03-04).

**Likely files:** `payment.service.ts`, `payment.controller.ts`, `payment.routes.ts`, `payment.schema.ts` (path params schema), `payment.openapi.ts`, the matching tests, `index.ts`, `README.md` and `ROADMAP.md`.

**Open decision:** the roadmap gives ownership to BE-03-06. If BE-03-03 ships without it, any signed-in user can read any payment, including its owner's email, as long as they know the ID.

**How it behaves**
- **Owner:** gets `200` with the same payment shape that `POST /payments` returns, without the internal `version` and `idempotencyKey` fields.
- **Admin:** gets `200` for any user's payment.
- **Another user's payment:** returns `404 payment-not-found`, identical to an unknown ID, so the endpoint doesn't reveal which IDs exist.
- **ID that isn't a UUID:** returns `400 validation-error` pointing at `/id`.
- **No token:** returns `401`.

The endpoint is registered in the OpenAPI spec with those responses and bearer auth.

**Docs**
- The task doc is [tasks/BE-03-03-get-payment.md](tasks/BE-03-03-get-payment.md).
