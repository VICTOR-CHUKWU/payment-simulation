### Claude

No. I expect Swagger UI to work with helmet as configured. I just haven't opened it in a browser yet.

Helmet sends a Content Security Policy header, which tells the browser which scripts, styles and images a page may load. Swagger UI is the one HTML page these services serve, so it's the only page that policy could break. Some Swagger setups do break under it, usually because they use inline `<script>` blocks.

I checked this one in the swagger-ui-express source, and it should be fine:
- **Scripts:** it loads only external files from the same origin (`swagger-ui-bundle.js`, `swagger-ui-standalone-preset.js`, `swagger-ui-init.js`). Helmet's default `script-src 'self'` allows those.
- **Styles:** its inline `<style>` blocks are allowed, because helmet's default `style-src` includes `'unsafe-inline'`.
- **Images:** its `data:` images are allowed by the default `img-src 'self' data:`.
- **Try it out:** these requests go to the same origin, which the default `default-src 'self'` allows.

The only part I'm less sure of is helmet's `upgrade-insecure-requests` directive, since the docs are served over plain `http://localhost`. Major browsers don't upgrade localhost requests, so it shouldn't matter.

That's why the task doc includes a step to open `/docs` and run **Try it out** on login: to confirm the source reading. If it did fail, the fix would be a small adjustment to the policy for `/docs` only, and the rest of the plan would stay the same.
