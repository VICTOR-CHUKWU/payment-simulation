**Approach.** Each payment record carries its own `outbox` list of events waiting to be sent to NATS. The event is added in the same compare-and-set write that changes the status. That keeps the status and its event from drifting apart, because the repository can only update one record at a time and can't write two collections together. A relay inside the payment service then publishes the events, oldest first per payment, and removes them once NATS accepts them.

**Your two choices, as written into the doc:**
- **When events are published:** right after each write, on a timer for anything left over, and once at startup.
- **Correlation ID:** `POST /payments` stores its request ID on the payment, and the background processor's events reuse it. An admin PATCH uses its own request ID.

**Defaults I picked without asking.** They're flagged in the doc's Source Context; change any there before implementation:
- `outbox` and `correlationId` are optional fields, so existing data files load without migration. Neither ever appears in API responses or the OpenAPI spec.
- Each event, including its ID, is built at the status change rather than at publish time, so a republish sends the same ID.
- A new env var, `OUTBOX_RELAY_INTERVAL_MS`, defaults to `1000` with a minimum of `10`.
- Published entries are removed rather than marked as published.
- On shutdown the relay stops after the processor and before the NATS connection drains.

**Trade-offs to be aware of:**
- **Delivery is at least once.** If the service crashes after publishing but before removing the entry, it sends the event again. NATS drops a repeat within 2 minutes; after that, the BE-05 consumers have to dedupe it.
- **Writes conflict more often.** Removing an entry bumps the payment's `version`, so a concurrent admin PATCH or processor step will sometimes conflict. It retries, as it does today: `transitionPayment` re-reads and tries up to 3 times.
- **No backfill.** Payments created before this change don't get events for their earlier status changes.

### Claude

The doc picks six defaults and accepts three trade-offs. I'd keep all of them, but each one below says what it means, what the alternative is, and when you'd want to change it.

## Default picks

1. **Old payments still load.** Payments already in `payments.json` don't have the two new fields (the outbox list and the correlation ID). Making both fields optional lets old data load as it is. The alternative is to require them and migrate old data, which is extra work for no gain. Keep it.

2. **The outbox and correlation ID stay out of API responses.** They are internal bookkeeping, so `GET /payments/:id` looks exactly as it does today. The alternative is to show them to admins for debugging. Change this only if you want to see unsent events through the API rather than in the data file.

3. **An event gets its ID once, when the status changes.** If the service has to send the event again, it sends the same ID. NATS and the notification service use that ID to spot the repeat and ignore it. If the ID were created at send time instead, a resend would look like a brand-new event and the user could get two emails. Keep it. This is what makes resending safe.

4. **Leftover events are retried every second.** The new `OUTBOX_RELAY_INTERVAL_MS` setting defaults to 1000 ms. It only matters when a send fails, for example while NATS is down. A lower value recovers faster after an outage but checks storage more often. A higher value does less work but leaves events waiting longer. One second matches how often the processor checks for payments.

5. **Sent events are deleted from the payment.** Each payment's waiting list empties once its events go out. The alternative is to mark them as sent and keep them, which gives you a history on each payment but makes the data file grow forever. The `PAYMENTS` stream already keeps every event for 7 days, so a second copy isn't needed.

6. **On shutdown, the sender stops after the processor and before NATS disconnects.** The processor's last status changes still get sent, and no send is cut off halfway. There's no real alternative here.

## Trade-offs

1. **An event can occasionally be sent twice.** Suppose the service sends `payment.succeeded`, then crashes before it deletes that event from the waiting list. On restart it sends the event again.
   - Within 2 minutes, NATS drops the repeat by itself.
   - After 2 minutes, the stream stores it twice, and the notification service has to ignore the second copy. That check is already planned in BE-05-02.
   - Avoiding this completely needs much heavier machinery. The usual approach, and the one I recommend, is to accept it.

2. **Status updates will sometimes collide and retry.** Deleting a sent event counts as a change to the payment. If an admin PATCH lands at that exact moment, the two writes collide. The PATCH re-reads the payment and tries again, up to 3 times, and the admin never notices. It only fails, with a `409`, if it collides 3 times in a row, which is very unlikely.
   - The alternative is to store waiting events separately from the payment. That removes the collisions but loses the guarantee that the status change and its event are saved together. Without that guarantee, a crash between the two saves could change a status with no event to say so.
   - I'd accept the collisions.

3. **Payments created before this change won't get events for their past status changes.** A payment that is already `succeeded` will never send `payment.created` or `payment.succeeded`. A payment still in progress will send events from its next status change onward.
   - This only matters if you have payment data you want to keep. Local dev data can be wiped.
   - The alternative is a one-time step at startup that creates the missing events. I'd skip it unless you have data worth keeping.

If you want to change any of these, tell me which and I'll update the task doc.

> so the outbox is the nats event right?

### Claude

Not quite. The outbox is not NATS. It's a waiting list of events saved inside the payment record, in your payment service's own storage (`payments.json`). Each item in that list is a NATS event that hasn't been sent yet.

Here is what happens to one event:

1. **The status changes.** For example, the processor moves a payment to `processing`. In the same save, the service builds the `payment.processing` event and puts it in that payment's `outbox` list. At this point nothing has gone to NATS yet.
2. **The relay sends it.** The relay reads the outbox and publishes the event to the NATS `PAYMENTS` stream. The event sent is exactly the one that was saved, with the same `eventId`.
3. **The event leaves the outbox.** Once NATS accepts it, the relay deletes it from the list. From then on the event lives in NATS, and the outbox is empty again (`[]`).

A stored payment looks like this while an event is still waiting:

```json
{
  "id": "ee553ed4-...",
  "status": "processing",
  "correlationId": "manual-check-1",
  "outbox": [
    { "correlationId": "manual-check-1",
      "event": { "eventId": "670f...", "type": "payment.processing", "data": { ... } } }
  ]
}
```

**Why not publish straight to NATS?** The save to `payments.json` and the publish to NATS are two separate steps, and either can fail on its own. If the service saved `processing` and then NATS was down or the process crashed, the event would be lost for good. Saving the event together with the status means it can't be lost. If NATS is down, the event just waits in the outbox until NATS is back. That's what you saw in the outage check: the 3 events sat in `payments.json` and went out about a second after NATS started.

### Claude

Close. Two corrections:

1. **Every status change fills the outbox, including the creation.** There isn't one outbox step after the processor finishes. A payment produces 3 events over its life, and each goes into the outbox at the moment its status changes.
2. **The relay doesn't send to the notification service directly.** It publishes to the NATS `PAYMENTS` stream, and the notification service reads from that stream. The two services never talk to each other directly.

The full flow:

| Step | Who | What happens to the payment | Outbox after the step |
|---|---|---|---|
| 1 | User calls `POST /payments` | Saved as `pending` | `[payment.created]` |
| 2 | Relay (kicked right away) | Publishes to NATS, removes it | `[]` |
| 3 | Processor (within about 1 s) | Claims it, status becomes `processing` | `[payment.processing]` |
| 4 | Relay | Publishes, removes it | `[]` |
| 5 | Simulated gateway (1 to 5 s later) | Processor records `succeeded` or `failed` | `[payment.succeeded]` |
| 6 | Relay | Publishes, removes it | `[]` |
| 7 | Notification service | Reads the events from the stream and sends the in-app notification and email | n/a |

Each status change and its event are saved together. Steps 2, 4 and 6 usually happen within milliseconds, so in the `payments.json` you have open, finished payments show `"outbox": []`. An entry only stays there while NATS is down, like in the outage check.

Step 7 doesn't exist yet. The notification service creates the `PAYMENTS` stream at startup but doesn't read from it. Consumers arrive in BE-05-01, and in-app notifications and emails in BE-05-03 and BE-05-04. Until then the events just sit in the stream for 7 days.

An admin `PATCH /payments/:id/status` follows the same path as the processor. It changes the status, adds the event in the same save, and the relay publishes it.
