Your `roadmap-todo` skill is at `~/agent-skills/skills/roadmap-todo/`. It keeps a single roadmap file per repo that lists feature-sized work. It only writes the plan. It never writes code.

## How to trigger it

Type `/roadmap-todo` and say what you want. You can also just ask in plain words ("add X to the roadmap"), and I'll pick it up. Examples for this repo:

- **Start one:** `/roadmap-todo create a roadmap for payment-be: Paystack integration, webhooks, refunds, idempotency keys, reconciliation job`
- **Add an item:** `/roadmap-todo add "multi-currency support" under Payments, todo`
- **Change a status:** `/roadmap-todo mark webhooks as in-progress, refunds blocked on provider sandbox`
- **Reorganise:** `/roadmap-todo split reconciliation into daily job + mismatch alerts` or `reorder by priority`
- **Close or archive:** `/roadmap-todo mark idempotency done, link tasks/003-idempotency.md`

## What you get

A lean Markdown file, grouped by area or phase, with a status legend. Each area has a table like this:

```markdown
## Payments Core

| # | Item                 | Status      | Task doc                  |
|---|----------------------|-------------|---------------------------|
| 1 | Paystack integration | done        | tasks/001-paystack.md     |
| 2 | Webhook handling     | in-progress | tasks/002-webhooks.md     |
| 3 | Refunds              | blocked     | —                         |
```

If the repo has no status scheme yet, it uses these statuses: `todo`, `in-progress`, `blocked`, `done`, `deferred` and `cancelled`.

## Rules it follows

- **Short entries:** each one is a title, a status and an optional link. If an entry needs more than 2–3 lines, it suggests a task doc instead of making the entry longer.
- **Feature-sized items only:** small steps like "add DTO" or "write migration" don't get their own row.
- **Targeted edits:** it changes only what you asked for and keeps your existing format and numbering.
- **No implementation.** Even if you say "add webhooks", it only adds the row.

## How it fits with your other skills

1. **`roadmap-todo`** lists what's planned and where each item stands.
2. **`task-doc`** (or **`task-doc-intake`** first, if the scope is still fuzzy) writes the detailed plan for one roadmap item. You then link that doc in the item's "Task doc" column.
3. **`task-doc-delivery-loop`** builds that task doc, all the way to a draft PR.
4. Back in **`roadmap-todo`**, you mark the item `done`.

You can also ask it for an `html-artifact` board when you want to see the roadmap as a page for planning. It won't offer one after routine status updates.

A good first step is to give me a rough list of what you want payment-be to do and run `/roadmap-todo create…`.

> is Biome via ultracite better than eslint and preetier?

### Claude

For this project, yes, though not by a wide margin. Both are solid choices.

**Why Biome via Ultracite fits here:**
- **One tool instead of two.** Biome both lints and formats, so you don't have to stop ESLint and Prettier from fighting over the same rules.
- **Much faster.** It's written in Rust and checks a monorepo almost instantly, which you'll notice in pre-commit hooks and CI.
- **Very little config.** Ultracite is a strict preset on top of Biome, so you get sensible, opinionated rules without writing them yourself.
- **It matches your setup.** You already have an `ultracite-standard` skill, so the tooling and your own conventions line up.

**Where ESLint and Prettier still win:**
- **Bigger plugin ecosystem.** There are framework- and library-specific plugins Biome doesn't have. A plain Express and TypeScript backend doesn't need any of them, though.
- **Mature type-aware rules.** typescript-eslint uses the TypeScript compiler to catch things like an un-awaited promise (`no-floating-promises`). That matters in a codebase built around async work. Biome has added its own version of some of these rules, but it's newer and covers less. Check which ones Ultracite turns on when you set it up.
- **Familiarity.** Most reviewers know ESLint configs at a glance.

**My recommendation:** keep Biome via Ultracite, and turn on TypeScript's `strict` mode. If you later find Biome missing un-awaited promises, you can add typescript-eslint with just that rule rather than switching tools.

The roadmap already says Biome via Ultracite, so nothing needs to change unless you'd rather switch.

> i want to ask the assesment mentioned in memory adapter and json file adapter, does that mean no db no schema, no typeorm? no entity

### Claude

Yes. There's no database server, no ORM such as TypeORM or Prisma, no migrations and no ORM entity classes. The brief says in-memory or JSON-file persistence "for simplicity", so a real database would add setup work for whoever runs the project and earns nothing extra.

You still have models and schemas, just not database ones:

- **Models:** plain TypeScript types for `User`, `Payment` and `Notification`. These take the place of entities.
- **Schemas:** Zod schemas that check the shape of request bodies and event payloads. You can also use them to check records loaded from the JSON file, so a corrupted or hand-edited file fails loudly instead of quietly.

**How each adapter works:**
- **In-memory:** a `Map<id, record>` inside the service. It's fast, it's used in tests, and the data is gone on restart.
- **JSON file:** one file per service, e.g. `data/payments.json`. The service loads it on startup and rewrites the whole file on each change. Writes go through a queue, so two requests can't overwrite each other's changes (BE-01-08).

Both adapters sit behind the same repository interface, with methods like `create`, `findById`, `update` and `findMany`. The service code never knows which one it's using.

The interface also gives you an easy answer if an assessor asks "how would this scale?": adding a Postgres adapter, with TypeORM or Prisma, means writing one new class and changing nothing else. That's worth a line in the design notes (BE-06-06). I wouldn't build it, though, because it goes against the "for simplicity" instruction.
