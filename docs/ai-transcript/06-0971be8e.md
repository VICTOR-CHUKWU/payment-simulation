## BE-01-06 inventory: central error model and error middleware

**Objective:** Every error response from every service uses one RFC 9457 format. A central Express middleware maps known, validation and unexpected errors to that format. The response never exposes internal details, and the real error reaches the logs.

### 1. What the code does today
- No error handling exists yet. A thrown route error goes to Express's default handler, which returns an HTML page and prints the stack with `console.error`. An unknown path gets Express's HTML 404. `createApp` mounts only `httpLogger` and `healthRouter` ([services/payment/src/app.ts](services/payment/src/app.ts)).
- **Log leak to avoid:** if a JSON body fails to parse, body-parser 2.3.0 attaches the raw body to the error (`createError(400, err, { body: str, type: 'entity.parse.failed' })`, `read.js:164`). pino's error serializer copies every enumerable key (`pino-std-serializers/lib/err.js:28`). If that error were logged, a raw `{"password":…}` string would be written to the logs, and the redaction paths would not catch it because the body is a string, not an object.
- Other body-parser errors carry a `status` and `type`: 413 `entity.too.large`, 415 `charset.unsupported` / `encoding.unsupported`, 400 `entity.parse.failed`.
- BE-01-05 left a follow-up for this milestone: for unexpected errors, set `res.err = err` so pino-http logs the real error rather than "failed with status code 500", and include the request ID in the response body.
- `parseEvent` throws a raw `ZodError` or `SyntaxError` ([libs/shared/src/nats.ts:53](libs/shared/src/nats.ts#L53)). Those are consumer errors, not HTTP errors, so they are out of scope here.

### 2. Proposed scope
A new module, `libs/shared/src/errors.ts`, exported from `index.ts`:

- **`problemDetailsSchema` (Zod):** `type`, `title`, `status`, `detail?`, `instance`, plus these extension fields:
  - `code`: a stable string a client can branch on
  - `requestId`
  - `errors?`: a list of `{ pointer, detail, code }`

  BE-01-09 registers this schema in OpenAPI, and the tests check response bodies against it.
- **`AppError` class:** takes `status`, `code`, `title`, an optional `detail`, extra fields, an optional response `headers` (for example `WWW-Authenticate: Bearer` for a 401) and a `cause`.
  - Helper constructors: `badRequest`, `unauthorized`, `forbidden`, `notFound`, `conflict`, `unprocessable`, `serviceUnavailable`.
  - A domain error such as "invalid state transition" or "version conflict" becomes an `AppError` with its own `code`.
- **`notFoundHandler`:** a catch-all for unknown routes that returns a 404 problem.
- **`errorHandler`:** the last middleware. It maps each kind of error as follows:

| Error | Response |
|---|---|
| `AppError` | Its own status, code and detail |
| `ZodError` | 400 `validation-error`, with an `errors[]` entry per issue: the Zod path converted to a JSON Pointer, plus the message and the issue code |
| body-parser / `http-errors` 4xx | 400, 413 or 415 with a generic detail; the raw `body` is never logged or echoed |
| Anything else | 500 `internal-error` with a fixed generic detail; never the message or the stack |

  Every response:
  - is `application/problem+json`
  - carries `instance` (the request path) and `requestId` (`req.id`)
  - goes out with `Cache-Control: no-store`

  For logging, the handler sets `res.err` only on 5xx responses, so pino-http logs the real error exactly once. For 4xx responses, `warn` plus the status is enough, which keeps client payloads out of the logs. If headers were already sent, it passes the error to `next(err)`.
- **Services:** `createApp` mounts `notFoundHandler` and `errorHandler` after the routes. The `/health/ready` 503 body does not change, because it is an existing contract.
- **Tests:**
  - `errors.test.ts` (supertest on a bare app): each row of the table above, a sync throw and an async throw (Express 5), malformed JSON with a password in the body (neither the response nor the logs contain it), a 500 that hides its message but logs the stack, `requestId` matching `x-request-id`, and an `AppError` adding a header.
  - In each service, the `app.test.ts` 404 test now checks the problem body.
- **Docs:** add an "Errors" section to the README with an example response and the list of codes; update the roadmap row.

### 3. Decisions I made (please confirm or change)
1. **Format: RFC 9457** rather than a custom envelope such as Stripe's `{ error: {...} }`. It is the IETF standard, and the Zalando, Microsoft and Spring guidelines use it.
2. **`type` values:** `about:blank` for plain HTTP statuses (404, 500, 413 and so on), where `title` is the standard status phrase. Errors specific to this service get a stable tag URI such as `tag:payment-be,2026:validation-error`. RFC 9457 allows tag URIs when there is no site to resolve the URI against, and this project has none. `code` repeats the last segment so clients have a simple key to branch on.
3. **Validation failures return 400**, not 422. This follows Google AIP-193, Microsoft and Spring. 422 stays available for semantically invalid requests such as an illegal payment transition, if BE-03-04 wants it.
4. **Validation field paths use JSON Pointer** (`/amount`, `/items/0/currency`), as in the RFC's own `errors` example.
5. **No request-validation middleware here.** This milestone only maps `ZodError`. BE-01-09 decides how routes declare their schemas, since the OpenAPI spec is generated from them.

## What's in [errors.ts](libs/shared/src/errors.ts)

The file has four parts. Only parts 1 and 2 are things you'll call in service code.

### 1. The response format (lines 5–55)
- **`problemDetailsSchema`** ([line 5](libs/shared/src/errors.ts#L5)) is the Zod schema for every error body. Its fields are `type`, `title`, `status`, `detail`, `instance`, `code`, `requestId` and optional `errors`. It will be registered in OpenAPI later (BE-01-09), and the tests check responses against it.
- **`ProblemDetails` / `ProblemFieldError`** are the TypeScript types inferred from that schema.
- **The constants and helpers from line 23 on are private:** the `about:blank` and tag-URI prefixes, the fixed messages for client errors, the fixed 500 body, `kebab()` and `statusPhrase()`.

### 2. What you throw (lines 57–131)
- **`AppError`** ([line 68](libs/shared/src/errors.ts#L68)) is the one error class for expected failures. It carries everything the response needs: `status`, `code`, `title`, `detail`, `type`, `headers` and an optional `cause`, which is logged but never sent to the client.
- **The helpers** ([lines 125–131](libs/shared/src/errors.ts#L125-L131)) are `badRequest`, `unauthorized`, `forbidden`, `notFound`, `conflict`, `unprocessable` and `serviceUnavailable`. `problemFactory` ([line 114](libs/shared/src/errors.ts#L114)) creates each one for a fixed status, so you rarely call `new AppError` yourself. They work in two modes:

```ts
throw notFound("Payment not found.");
// 404, type "about:blank", title "Not Found", code "not-found"

throw conflict("Payment was updated by someone else.", { code: "version-conflict" });
// 409, type "tag:payment-be,2026:version-conflict", code "version-conflict"
```

  - **Without a `code`:** you get a plain HTTP error.
  - **With a `code`:** you get an error specific to this service, which clients can branch on.

  You can also pass `headers`, `title` or `cause`:

```ts
throw unauthorized("Missing token.", { headers: { "WWW-Authenticate": "Bearer" } });
throw serviceUnavailable("Gateway timed out.", { cause: err }); // cause is logged, never sent
```

### 3. Converting any error into a response body (lines 133–240, private apart from `toJsonPointer`)
`toProblem` ([line 214](libs/shared/src/errors.ts#L214)) decides what kind of error it was given:

| What was thrown | Converted by | Result |
|---|---|---|
| `AppError` with a status from 400 to 599 | `appProblem` | Its own status, code and detail |
| `ZodError` | `validationProblem` | 400 `validation-error`, plus `errors[]` with a JSON Pointer per field (`toJsonPointer`) |
| An object with a 4xx `status` (body-parser errors, for example) | `clientStatus`, `clientProblem` | That status with a fixed message, such as `malformed-json` or `payload-too-large` |
| Anything else | `INTERNAL_PROBLEM` | 500 `internal-error` with the fixed detail "An unexpected error occurred." |

`toError` and `safeString` turn thrown values that aren't `Error` objects (a string, say) into an `Error` so they can be logged. `instancePath` removes the query string from the path. `toJsonPointer` is exported only so the tests can use it; `index.ts` does not export it.

### 4. The two middlewares (lines 242 onward)
- **`notFoundHandler`:** when no route matched, it passes `notFound(...)` on to the error handler.
- **`errorHandler`:** the last middleware in each app. For each error it:
  1. checks whether the response has already started. If so, it records the error for the logger and drops the connection (`res.destroy()`), because a new body can't be sent.
  2. calls `toProblem(err)`.
  3. for a 5xx, sets `res.err = err` so pino-http logs the real error and stack once. 4xx errors are not logged with the error, which keeps client data out of the logs.
  4. sends the problem with `application/problem+json` and `Cache-Control: no-store`, adding `instance` and `requestId`.

Every service already mounts both, in this order, in `app.ts`:

```ts
app.use(httpLogger(logger));   // sets req.id, writes the log line for each request
app.use(healthRouter(checks));
// ← your routers go here
app.use(notFoundHandler);
app.use(errorHandler);
```

Mount your routers between `healthRouter` and `notFoundHandler`. A router mounted after `notFoundHandler` is never reached.

## In your service code

Import from the shared package and throw. Don't catch errors just to turn them into responses:

```ts
import { conflict, notFound } from "@payment-be/shared";

router.get("/payments/:id", async (req, res) => {
  const payment = await repo.findById(req.params.id);
  if (!payment) throw notFound("Payment not found.");
  res.json(payment);
});

router.post("/payments", async (req, res) => {
  const input = createPaymentSchema.parse(req.body); // bad input → ZodError → 400 validation-error
  res.status(201).json(await service.create(input));
});
```

- **Validation:** call `schema.parse(...)` directly. A `ZodError` becomes a 400 with field paths automatically.
- **Throwing deeper down:** a service or repository function can throw `conflict(..., { code: "version-conflict" })` too. It reaches the handler however deep the call stack is.
- **Don't** call `res.status(4xx).json(...)` for errors. Responses from the error handler all have the same shape and carry the request ID.

## How an unhandled error reaches the handler

```
route handler throws, or its async function rejects
        │   (Express 5 catches both and calls next(err) for you)
        ▼
errorHandler(err, req, res)
        │   toProblem(err): not an AppError, ZodError or client error
        ▼
500 { code: "internal-error", detail: "An unexpected error occurred.", requestId }
res.err = err  →  pino-http logs ONE "error" line with the real message, stack and correlationId
```

The client never sees the message or stack. To investigate, search the logs for the `requestId` from the response; it matches the log line's `correlationId`.

**Where the error handler does not reach:**
1. **Callbacks outside the request's promise chain.** Errors thrown in `setTimeout`, an event emitter or a stream callback inside a handler are not caught by Express. Use `await`, or catch the error and call `next(err)`.
2. **Code that doesn't run inside an HTTP request.** This includes the payment processor (BE-03-05) and NATS consumers (BE-05). The error handler is HTTP middleware, so those need their own `try`/`catch` and logging, plus ack/nak decisions in consumers. Those belong to the later milestones.
