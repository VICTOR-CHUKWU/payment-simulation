## BE-01-07 scope

**Goal.** `libs/shared` gets a generic, async `Repository<T>` interface with compare-and-set updates, plus an in-memory adapter. BE-01-08's JSON-file adapter will implement the same interface and pass the same tests.

**What exists today.** There's no persistence code yet; `libs/shared/src` holds only config, errors, events, health, logger, nats, server and shutdown. The BE-01-06 follow-up in [tasks/BE-01-06-error-model.md](tasks/BE-01-06-error-model.md) expects a failed compare-and-set to map to `409` with code `version-conflict`. Files ending in `.test.ts` are already left out of the build ([libs/shared/tsconfig.json](libs/shared/tsconfig.json)).

**Proposed design** (new `repository.ts` and `memory-repository.ts`):
- **Record type:** `interface Versioned { id: string; version: number }`. The caller creates the ID with `randomUUID()`, so idempotency keys and the outbox can know it before the insert.
- **Methods:**
  - `get(id): Promise<T | undefined>`
  - `find(predicate?): Promise<T[]>`, returned in insertion order. This covers lookups by owner, by status (resuming payments after a restart) and by idempotency key.
  - `insert(record: Omit<T, "version">): Promise<T>`, which stores the record with `version: 1`.
  - `update(id, expectedVersion, patch): Promise<T>`. It does a shallow merge, can't change `id` or `version`, and bumps `version` by 1.
- **Async on purpose:** the in-memory adapter doesn't need it, but the file adapter will.
- **Copies in and out:** each method stores and returns `structuredClone` copies, so a caller can't change stored state by mutating an object.
- **Atomic compare-and-set:** the in-memory version check and write run with no `await` between them, so nothing can run in between.
- **Errors:**
  - `VersionConflictError` extends `AppError`: 409, code `version-conflict`, and a generic detail. The existing error handler returns it with no extra code, and the processor can still catch it with `instanceof`.
  - `update` on an unknown ID throws `RecordNotFoundError` (an `AppError`, plain 404 `not-found`).
  - A duplicate ID on `insert` throws a plain `DuplicateRecordError`, which becomes a 500. With UUIDs, a duplicate only happens through a bug, so it shouldn't be a client error.
- **Factory:** `createMemoryRepository<T>()`. Everything is exported from `index.ts`.

**Tests**
- A reusable contract suite, `repository-contract.ts` (not exported), run by `memory-repository.test.ts`. BE-01-08 reuses it for the file adapter. It covers:
  - insert, get and find
  - version increments
  - a stale version causes a conflict and leaves the stored record unchanged
  - two concurrent updates at the same version: exactly one succeeds
  - an unknown ID, a duplicate ID, and copy isolation
- One supertest check that `VersionConflictError` returns 409 problem+json with code `version-conflict`.

**Out of scope**
- Delete (no milestone needs it)
- Pagination and sorting (BE-07-02)
- Zod validation of stored records, the storage env var and adapter selection, and the readiness check (BE-01-08)
- Payment, user and notification models
- Unique secondary indexes, such as on idempotency keys (BE-03-07)

## What the doc defines

It defines a TypeScript **interface** plus a **factory** that returns an object implementing it:

```ts
interface Repository<T> {
  get(id)                          // findById
  find(predicate?)                 // findAll, or filtered
  insert(record)                   // create
  update(id, expectedVersion, patch)
}

createMemoryRepository<Payment>()  // the "db" side (BE-01-08 adds the JSON-file one)
```

There's no `delete`, because no milestone needs it.

Your layering maps onto it like this:

```
paymentRouter (controller)      parses input with Zod, calls the service
  → PaymentService               state machine, ownership checks, events
    → PaymentRepository          domain queries such as findByUser, findPending
      → Repository<Payment>      generic storage (in-memory or JSON file)
```

The payment repository **wraps** the generic one rather than extending it:

```ts
function createPaymentRepository(store: Repository<Payment>) {
  return {
    ...store,
    findByUser: (userId: string) => store.find((p) => p.userId === userId),
  };
}
```

I chose this over an abstract class for two reasons:
- **Which storage to use:** the env var decides between memory and JSON file at startup (BE-01-08). With inheritance you'd need `MemoryPaymentRepository` and `FilePaymentRepository` classes, or the storage passed in anyway.
- **Testing:** a service test can pass a plain in-memory repository with no subclass.

If you prefer classes, `class PaymentRepository { constructor(private store: Repository<Payment>) {} }` works the same way. It's a style choice for BE-03-01, not something this task fixes.

## Why I'd leave out a generic service

The layering itself is right, but a generic `BaseService<T>` would mostly pass calls straight through to the repository. The useful part of each service is specific to it:
- **Payment:** checking allowed status transitions, ownership rules, and publishing events.
- **Auth:** hashing passwords and issuing tokens.
- **Notification:** deduping per channel.

A shared base class would either hide those rules or have every method overridden. So each service gets its own small service module, created in its own milestone (BE-02-01, BE-03-01, BE-05-03), each built on `Repository<T>`.

Should I keep the doc as it is, or change it? I could switch to an abstract base repository class, or add a short "how services use this" section showing the controller → service → repository pattern so later milestones follow it.

## 1. Why the repository errors aren't in `errors.ts`

`errors.ts` is the **HTTP error model**: the problem+json body, `AppError`, generic helpers like `notFound()` and `conflict()`, and the Express error handler. It knows nothing about storage.

`VersionConflictError` and its two siblings belong to the **repository contract**. They're part of what `update` and `insert` promise:
- **Together with what throws them:** the JSON-file adapter in BE-01-08 must throw exactly these errors too. Keeping them next to the interface they describe keeps the contract in one place.
- **Dependencies go one way:** `repository.ts` imports `AppError` from `errors.ts`, and nothing goes the other way. If they lived in `errors.ts`, the HTTP layer would hold storage concepts. Later, payment's "invalid status transition" error and auth's "invalid credentials" error would end up there too. It would become a grab-bag of every error in the system.
- **Same as Spring:** `OptimisticLockingFailureException` lives in the data-access module, not the web module, even though the web layer turns it into a 409.

The rule is that each error lives with the code that throws it, and `errors.ts` holds the shared base class and the HTTP mapping.

## 2. Why there's no separate `libs/repository`

A separate package would cost more than it gives at this size:
- **Setup cost:** it needs its own `package.json`, tsconfig, build reference, export conditions and dependency entries in every service.
- **It would depend on shared anyway:** the repository uses `AppError`, so it would need `libs/shared` either way.
- **No consumer wants only part of it:** all three services use the logger, the errors, NATS and the repository. Splitting packages pays off when consumers need different subsets, or when a package is versioned or published on its own. Neither applies here.
- **It contradicts the project rules:** AGENTS.md says "Shared code (event contracts, NATS client wrapper, logger, error model, config, auth middleware) goes in `libs/shared`." Changing that is a project decision, not part of this task.

Your concern that `shared` will get too big is fair, though. The cheaper fix is **folders inside `libs/shared`**, not more packages. BE-01-08 is a natural point for that, once the JSON-file adapter makes it three repository files:

```
libs/shared/src/repository/
  repository.ts          interface + errors
  memory-repository.ts
  file-repository.ts     (BE-01-08)
  repository.test.ts
```

Imports from `@payment-be/shared` wouldn't change, because `index.ts` re-exports everything.
